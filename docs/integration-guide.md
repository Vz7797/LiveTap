# 接入方开发指南

适用接口版本：`v1`；订阅状态心跳从采集服务 `0.3.2-m3.2` 开始提供。详细请求和字段以 [api.md](api.md) 为准，服务职责以 [design.md](design.md) 为准。

LiveTap 是独立部署的采集节点：只管理自己的房间，不知道其他节点的存在。选节点、迁移、业务场次和下游处理（例如 AI 自动回复、语音播报）都由接入方负责；本项目提供接口、SDK 和本指南。以下业务策略和数值都是建议，接入方可按实际产品和容量调整，并自行验证。

## 1. 推荐接入顺序

1. **登记节点。** 运维在每个采集节点创建专用接入方，设置配额和可选来源 IP 网段。API Key 只显示一次，建议放在业务服务的秘密配置或加密存储，不放在浏览器、源码、URL、日志里。业务后台登记节点北向地址。加机器时只需加登记信息。
2. **读取节点信息。** 启动和定时巡检调用 `GET /v1/node`，先比较 `api_version`。不兼容时建议告警、停止分配；`version` 只是软件版本，不用它代替接口版本。可从每 15 秒巡检、45 秒指标有效期开始调试。
3. **选节点。** 建议从启用、指标新鲜、健康、未冷却且有容量的节点里选剩余容量最多的一个，例如初始健康门槛 80。还要考虑本接入方配额，处理 `capacity_exceeded`。同一规范化房间固定在同一节点，别因为另一个节点空闲了一点就搬家。
4. **订阅。** `POST /v1/subscriptions` 提供房间号或完整直播链接。保存响应的 `live_id`（规范化 web_rid）、订阅 ID、节点、商家和场次关系；不要混用上游 `room_id`、内部场次 ID 和直播间号。建议在业务侧用唯一约束防止并发把同一房间分到两台机器。`external_ref` 仅是回传标签，事件归属仍应核对本地订阅关系。
5. **续租。** 默认租约 120 秒，成功 Pong 会自动续租，但只在剩余不足一半时续，断流那一刻订阅最少只剩约 60 秒；建议配合 SDK `AutoRenew` 覆盖断流重连期间。`AutoRenew` 的 `onReleased` 和 Stream 的 `OnReleased` 会告诉你哪些订阅结束了：`lease_expired` 而业务还需要这个房间就立即重新订阅，`live_ended` 按下播处理。过期后旧 ID 不能复活，需重新订阅。等待开播默认超过 60 分钟会闲置释放，与租约续期独立，业务若需要更久应明确配置 `idle_release_seconds`。直播结束后节点会在 10 分钟内自行结束订阅（`live_ended`），见第 4 节。
6. **收事件。** 建议每个节点共用一条 `/v1/stream`，按订阅分发到各商家。`status` 更新状态和活性，`room_stats` 更新统计，只有经过筛选的互动才进入下游处理（例如 AI 回复）。隔离商家、账号和场次的队列、消息与去重记录。
7. **断线补拉。** 优先由 SDK 自动重连，携带该节点的 `boot_id` 和最后成功处理的订阅事件 `seq`。不因为一次断流立即搬房间。首次连接也可带 `since_seq=0` 补回订阅到连流之间的消息。
8. **需要时换节点。** 按下一节判断，再选健康且有余量的备用节点。建议先建立新订阅，切换本地归属，再退订旧订阅；切换期间的重复消息由持久去重挡住。新订阅失败则保留旧归属并提示，别循环搬家。不同节点的 seq 不能互相使用。
9. **退订。** 用户明确结束助播，或业务经过下播宽限确认场次结束后，调用 `DELETE /v1/subscriptions/{id}`，停止对应续租和本地任务。处理 `subscription_released`，不要把已释放的订阅一直当成正常。最后一个订阅退掉后自动任务释放；管理员手动任务保留。

迁移退订失败时建议重试并显示“旧订阅待清理”。注意全订阅 WS 的 Pong 会续租该接入方的所有有效订阅，**只停止该房间的 HTTP 续租还不够**。不要依赖它自己过期；优先重试显式退订。如果必须关闭旧流等待租约释放，需先为仍留在旧节点的其他房间安排明确的续租/收流方案，避免误停整批房间。API Key 的配额和身份也建议按业务部署隔离。

SDK 在 [../sdk/go](../sdk/go)，示例在 [../sdk/go/examples/minimal/main.go](../sdk/go/examples/minimal/main.go)。接入方可以复制到自己的仓库，保留来源/版本说明，或发布为内部依赖；避免用开发机绝对路径或 `go.work` 做部署依赖。`Node/Subscribe/Renew/AutoRenew/Unsubscribe/StatusBatch/Stream` 已覆盖上述接口。示例运行会真正订阅房间，离线开发请使用假节点。

## 2. 怎么判断该换节点

建议把两种时间分开保存：

- **每房最近收到事件的时间**：弹幕、礼物、统计、房间状态、状态心跳都算。其他房间的事件和连接级 hello/Ping/Pong 不算这个房间的事件。
- **最近收到上游消息的时间**：心跳里的 `extra.last_message_at`，用于观察上游是否有数据。它很久没变，甚至为 `null`，都不单独构成迁移理由。

默认每 60 秒有一条房间 `status` 心跳（`extra.code=heartbeat`）。它表达“房间仍在管理”，无需房间有人说话。建议自动静默迁移同时满足：

1. 这个房间最新已知状态为 **`collecting`（采集中）**。
2. 超过静默阈值没有该房间的任何事件，**包括心跳**。
3. 已尝试恢复原流，并有可用备用节点；切换前建议查一次房间状态，避免用过期状态作决定。

建议初始阈值为 **210 秒**（默认三次心跳加 30 秒余量）；改变心跳配置后可采用 `max(210 秒, 3 × 心跳间隔 + 30 秒)`。流持续给出新的 `collecting` 心跳时，即使没有弹幕，也不触发这种静默迁移。这个数值给调度、网络抖动和短暂重连留余量，后续应根据部署延迟调整。

| 最新状态 | 建议处理 |
|---|---|
| `collecting` | 有新事件就继续；全部事件静默超过阈值后，才考虑换节点 |
| `waiting` | 正在等开播，不因没有弹幕迁移；走下播宽限或等待逻辑 |
| `probing` | 正在确认上游状态，先等结果；反复换节点会重复探测 |
| `cooling` 或节点冷却 | 等冷却恢复，不分配新任务；已有采集连接可继续，不因冷却主动搬走 |
| `connecting/reconnecting/risk` | 展示状态和原因，观察原节点恢复，长期异常告警；不要套用采集中静默迁移 |
| `stopped/notfound` | 展示停止原因、核对房间和业务意图，不做循环迁移；`reason` 提示地区限制时，告诉商家该直播间在节点所在地区不开放，换节点或由商家处理 |

心跳遇到节点冷却时，未采集的启用任务显示 `cooling`，`base_state` 保留原状态。已经采集的连接仍显示 `collecting`，并带 `node_cooldown=true`；建议先等冷却，避免迁移引发新的受限请求。节点接口失联或版本不兼容时可先标记不可分配、告警；不要直接把等待开播的所有房间批量搬走。

**频繁换节点会重新探测、建连、获取游客身份，增加抖音请求和风控风险。** 建议迁移后至少观察 5 分钟再考虑同房间的下一次自动迁移，没有备用容量时只提示和退避。补拉收到的是旧状态，建议保留事件原时间；若补拉结束只有旧数据，再查询当前状态，不把历史心跳当成当前节点健康证明。

## 3. 事件进入下游处理前，建议先筛选

推荐先做持久去重，再按商家/场次筛选、合并和排队。`status`、`room_stats` 不进 AI 回复队列，点赞通常也只更新统计。可以先从下面这些默认值开始，观察响应延迟和播报占用再调：

| 项目 | 建议默认值 | 理由 |
|---|---|---|
| 欢迎进场 | 30 秒窗口合并；同一用户 5 分钟内不重复欢迎 | 大房间每人一句会挤占提问和播报时间 |
| 礼物致谢 | 独立 20 秒窗口，按用户/礼物合并 | 连击应汇总，避免把一次送礼拆成很多回复；注意上游累计数量不要反复相加 |
| 关注致谢 | 独立 30 秒窗口，按用户合并；分享与关注按 `social.action` 区分 | 减少同一观众重复触发，避免把分享误当关注 |
| 合并文本 | 最多念 3 个昵称，其余概括人数 | 避免长名单让下一条提问等很久 |
| 待处理合并任务 | 每场每类最多 1 个；已有任务只更新名单/数量 | 合并窗口结束后，也不能不断追加同类任务 |
| 非提问播报总频率 | 欢迎、礼物、关注合计最多 3 条/分钟 | 单类有限频仍可能合起来太密，要留出提问空间 |
| 队列总上限 | 每场最多 100 条，提问优先 | 内存和等待有上限；不是承诺每条都能回复 |
| 欢迎/致谢最长排队 | 30 秒；合并更新不重置最早等待时间 | 过时的欢迎没有价值，别无限延寿；调用 AI 前和播放前再检查一次 |

优先级建议：有效提问最高，礼物/关注其次，欢迎最低；普通闲聊、讲解任务的顺序可由产品决定。队列已满但有新提问时，建议先淘汰欢迎，再淘汰较低优先级的致谢、闲聊或讲解，给提问腾位置。若队列里已全是提问，仍需有界：合并重复提问或明确记录未处理，别无限扩容或伪装都回复了。

接入方也可以让欢迎/致谢使用固定模板，降低 AI 和语音合成开销；是否使用、对哪些用户使用由产品决定。建议用假消息验证“每分钟 300 条进场 + 30 条弹幕”的场景，观察提问等待时间、合并数、过期数和丢弃数，别用真实采集压测代替队列测试。

## 4. 开播与下播：一场直播一次订阅

节点按“**一场直播一次订阅**”工作，不会整夜探测已经下播的直播间（无意义，还会增加风控风险）：

1. **开播时订阅。** 商家在业务端开始助播时创建订阅。商家可以先订阅再开播：节点按轮询等待，最长 `idle_release_seconds`（默认 60 分钟），仍未开播就结束订阅（`idle_release`）。
2. **下播由节点确认。** 采集中的直播结束后，状态变为 `waiting`，原因是“直播已结束，10 分钟内未重新开播将停止检测”。10 分钟内重新开播会自动接上（下播后 2 分钟内的重开约 30 秒内接上，之后最多约 2 分钟）；超过 10 分钟仍未开播，节点停止检测该房间，并推送 `subscription_released`，`reason=live_ended`。
3. **下次开播重新订阅。** 收到 `live_ended` 后，把这场助播标为已结束，停止续租，不要立即重新订阅；商家下次开播时再创建新订阅（同一商家可复用同一 `external_ref` 规则）。

业务端的提示：

- 收到一次 `waiting` 不必立刻结束整场助播，网络抖动、断播重开都可能随后恢复。需要更早提示“疑似下播”时，可以从首次 `waiting` 开始计时；但**结束助播以 `live_ended` 为准**，不必再自己做一套 5 分钟、10 分钟的确认。
- `probing`、`reconnecting`、`cooling`、`risk` 不是下播信号，不要据此结束。
- 程序判断请看 `state` 和 `reason_code`（见[状态与原因码](api.md#状态与原因码)），不要解析 `reason` 中文文字，它的措辞可能调整。
- 商家主动点击结束助播是明确意图，可以立即退订，不用等 `live_ended`。
- 商家不再合作时退订即可；即使忘了退订，租约（默认 120 秒）到期后订阅也会结束，节点不会保留这个直播间。

## 5. 去重和缺口，建议按可恢复故障来设计

- 用 **`规范化 live_id + 抖音消息 id`** 做持久幂等键，字段都用字符串。seq 不能替代消息 ID，节点迁移后 seq 会不同。不同业务租户可按自己的归属隔离收据，但同一房间跨节点要落到同一份去重记录。
- 建议把消息收据、业务消息和入队结果原子保存（数据库事务或等价方案）；成功后才确认游标。默认可保留整个活动场次，结束后再保留至少 24 小时，按实际重试周期决定清理时间。单靠 SDK 的 10 分钟/每房 2000 条内存去重，挡不住进程重启后的重复回复。
- 本地产生的 `status` 没有抖音消息 ID，`id` 是空字符串；不要把所有空 ID 当成同一条，也不要把心跳送进 AI。它仍是正常订阅事件，成功处理后推进游标。
- 游标建议按节点和 `boot_id` 保存；只由成功处理且带顶层 `subscription_id` 的事件推进。`hello/gap/backpressure/subscription_released` 控制帧不推进游标。不同房间和过滤会造成 seq 跳号，跳号本身不是缺口证据。
- 断线期间结束的订阅，会在带游标重连后补发 `subscription_released`；从游标到重新订阅之间该房间的消息收不到，按缺口处理。`hello` 的 `subscriptions` 是本连接承载的订阅数，为 0 而业务仍在播时，要查询订阅并重新订阅，不能只等消息。
- 实现 SDK `OnGap`：记录节点、房间范围、原因、发现时间，并在商家端或后台提示“期间可能漏消息”。连接级缺口不能精确定位房间时，建议标记该连接涵盖的订阅范围，别编造漏失数量。SDK 没有 `OnGap` 时会返回 `GapError`。
- 补拉只保留每房最近 60 秒、最多 1500 条/1 MiB，单次最多 20000 条/32 MiB。实测 100 个直播间（订阅弹幕、进场、关注）断线 60 秒以内可完整补齐；更热闹的直播间或更长断线仍会收到 gap。节点重启、长时间断线、流量高或慢客户端都可能有缺口；恢复后收到事件不代表缺口消失。跨节点也没有共同历史缓存，建议迁移时明确记录可能缺口，不承诺零丢失。

## 6. 部署提醒

建议节点与接入方之间使用**受控可信内网，或 HTTPS/WSS**；跨公网必须用 HTTPS/WSS，不用明文 HTTP 传 API Key。在不完全可信的内网也建议启用 TLS。协议头、反向代理访问日志、错误追踪和导出文件都应避免保存 Authorization。

建议后台和北向分开监听（`LIVETAP_ADMIN_LISTEN` / `LIVETAP_LISTEN`），再限制访问来源；API Key 与后台登录不是同一种权限。反向代理需支持 WebSocket 升级和长连接，并给默认 15 秒 WS Ping 留足空闲超时；60 秒订阅心跳是业务状态通知，不替代 Ping/Pong。

版本升级建议先用本地假节点检查订阅、续租、补拉、缺口、跨节点去重和退订，再安排真实联调。本指南只说明接口和建议；不代表任何接入方的业务实现已经验收，也不代表真实抖音采集已在该接入方的环境中验证。
